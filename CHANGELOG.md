# Changelog

All notable changes to OpenLabelServer are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html)

## [Unreleased]

### Added

- Configuration loading (`backend/config.py`, `backend/main.py`, `backend/README.md`, `tests/test_config.py`): every setting the service reads from its environment is now loaded once, when the application is built, into a `Settings` object that `create_app` takes its database path and credentials from, so `OPENLABEL_DATABASE` and `OPENLABEL_AUTH` are read in one place instead of at their point of use. An unset variable and an empty one are the same default, which is how Compose passes a variable a deployment leaves out, while a value that is present but wrong still stops the application with a message naming the variable and, for `OPENLABEL_AUTH`, the principal and field at fault; an explicit database argument still wins over the configured one, so tests and the conformance suite keep injecting their own. The bind address, port, log level and `OLS_ENV` stay with the entrypoint and Compose because no backend code reads them, and the storage root is not a setting yet: assets are rows of the same SQLite database, so there is nothing outside it to configure a location for. `tests/test_config.py` covers the defaults, both variables, the empty-string rule and the application opening the configured file
- Authentication (`backend/auth.py`, `backend/main.py`, `tests/test_api_auth.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): the service now runs the API §4.2 credential layer when `OPENLABEL_AUTH` configures it — one JSON object naming principals with their §4.5 identity, their §4.6 roles and a `bearer_token` or an `ols_` `api_key` — and answers the §4.7 `401` with `WWW-Authenticate: Bearer realm="OpenLabelServer"` for a missing or invalid credential, the §4.6 `403` when an authenticated principal holds no role the operation accepts, and lets a Bearer token decide a request that carries both schemes (§4.2); every role reads and only `admin` writes, the system endpoints keep answering without credentials, `/v1/info` reports `capabilities.authentication` as the configuration decides, and without the variable the service stays the §4.1 implicit administrator and answers as before, so an existing deployment changes nothing. A malformed configuration stops the application with a message naming the principal and field at fault; the credentials are configured rather than issued because §4.3 and §4.4 are not implemented; `AP-108` and `AP-109` become `CP-API` conformance cases — the `401` challenge, the viewer's `403` that stores nothing, and the Bearer-first rule
- Render jobs (`backend/main.py`, `backend/storage.py`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`, `specs/api/openapi.yaml`, `backend/README.md`): `POST /v1/render-jobs` now accepts the API §8.7 submission and answers `202` with the OpenAPI `RenderJob` resource — a server-generated opaque `rnd_` id, `object: "render_job"`, `status: "queued"`, `progress: 0`, the `template_id` / `stock_id` the body named, and the `output` options it was accepted with (the published `pdf` / `300` dpi defaults when it names none). The submission is validated for the rules §8.7 and §5.4 state and no others: exactly one of `template_id` and `document`, else a `422` whose `errors[0].code` is `missing-template-or-document`; an `output.format` outside `pdf` / `postscript` or a `dpi` outside 72–2400, else a `422` on `output.format` / `output.dpi`; and a `stock_id` no catalog holds, else a `422` with `stock-not-found`. The submitted document is stored as sent rather than validated, because an effective RenderSpec only exists once §9.2.2 has translated a stock into it, so §9.1's validation belongs to the execution that builds it; for the same reason a `template_id` the catalog does not hold is not rejected at submission, since §8.7 states no such rule and §5.4 names no code for it. `GET /v1/render-jobs/{job_id}` answers the job or the §5.2 `404`, carrying the §5.5 `error` and the `completed_at` moment of a failed job, `GET /v1/render-jobs` lists the accepted jobs newest first in the §6.2 envelope and filters on the five §8.7 statuses (anything else is the §5.2 `400`), and `backend/storage.py` holds the section's lifecycle — `queued` → `processing` → `completed` / `failed`, and `cancelled` from either — refusing every other transition, so the future executor drives it rather than the API. `AR-107`, `AR-108`, `AR-109` and `AR-110` become `CP-API` conformance cases; cancellation, output download and job execution are not implemented yet
- Portable asset references (`backend/main.py`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`, `specs/api/openapi.yaml`): a stored template now names the uploaded assets it references by the API asset URIs this host serves, which is the rewrite API §9.5 asks for — an `assets[].source` or `fonts[].variants[].source` that hands back an upload, by the opaque `ast_` id or by the `/v1/assets/{id}/content` path on any host, is written as the URI that upload published, so the stored document does not carry the host its client happened to use; an external HTTPS URL and a base64 data URI are the specification's other two forms and are stored as sent, and a reference to an id nothing stored is left alone rather than turned into a URI that would answer `404`. Create and replace rewrite alike and the rewrite is stable, so reading a template back and storing it again changes nothing, and the OpenAPI descriptions of both operations say so; `AJ-107` becomes a `CP-API` conformance case for the storage half — the stored forms and the bytes the stored URI serves — while its rendering half stays open until the job pipeline exists
- Collection link headers (`specs/api/openapi.yaml`): the `200` responses of `GET /v1/stocks`, `GET /v1/calibrations` and `GET /v1/assets` now publish the API §6.3 `Link` header, with the section's relations and an example naming the operation's own path — all three operations carry it and only the templates collection documented it, so a client reading the contract alone could not tell the header was there. The description and the `rel="next"` / `rel="first"` ordering are the templates collection's own, so the four collection operations now read alike
- Idempotent asset uploads (`backend/main.py`, `backend/storage.py`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `POST /v1/assets` now honours the `Idempotency-Key` header API §10 publishes — a repeated key with the same upload answers the stored `201` and its body, naming the same `ast_` asset and creating no second one, while the same key carrying another body is the §5.2 `409` that stores nothing — which is RFC-0001's corrected replay semantics, so `AQ-102` becomes a `CP-API` conformance case. The key is remembered in an `idempotency` table beside the asset catalog for §10's 24 hours and is free again afterwards, the fingerprint compares the parsed upload (file digest, filename, part media type and the optional `name` and `content_type` fields) rather than the multipart encoding so a retry with a fresh boundary still matches, and a key whose asset has since been deleted is released rather than replayed. Job submission replay (`AQ-103`) and the no-key negative control (`AQ-104`) remain open
- Asset collection and deletion (`backend/main.py`, `backend/storage.py`, `tests/test_api_app.py`): `GET /v1/assets` now lists the stored assets in the §6.2 envelope — newest first with the id breaking a tie, `page` and `page_size` under the §6.1 bounds, and the `content_type` parameter OpenAPI publishes as this collection's filter, compared case-insensitively so `?content_type=IMAGE/PNG` matches an upload stored as `image/png`, while a media type nothing was uploaded as is an empty page rather than an error — and the page carries the §6.3 `Link` relations the other collections answer with; `DELETE /v1/assets/{asset_id}` removes the row and answers `204`, after which the metadata and content operations for that id answer the §5.2 `404` the unknown id earns, and both operations answer what `specs/api/openapi.yaml` documents for the path. The store gained the `all(content_type)` query with its newest-first ordering and the delete it needed to serve them, and the paging arithmetic moved into `_page`, which the template, stock, calibration and asset collections now share
- Assets (`backend/main.py`, `backend/storage.py`, `backend/requirements.txt`, `docker/ci/requirements.txt`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `POST /v1/assets` stores a file uploaded in the required `multipart/form-data` `file` field and answers `201` with the OpenAPI `Asset` resource — a server-generated opaque `ast_` id, the `name` (the uploaded filename when the optional field is omitted), the content type the §8.6 allowlist permits (the `content_type` field when it is given, otherwise the file part's own, and `application/octet-stream` when neither names one), the byte count and the SHA-256 of the stored bytes — while `GET /v1/assets/{asset_id}` answers that metadata with `url` naming the §9.5 content URI, `GET /v1/assets/{asset_id}/content` serves the stored bytes unchanged under their media type, an unknown id is the §5.2 `404`, and a content type the section does not allow is the §5.3 `422` that stores nothing; the bytes are a row of an `assets` table in the same SQLite database, `python-multipart` parses the upload and its own `422` for a missing `file` field is rewritten as the published problem document with a `file` entry, and `AR-105` becomes a `CP-API` conformance case. The collection's list and `DELETE` operations, the §10 `Idempotency-Key` replay and the §9.5 rewriting of template asset references to API URIs are not implemented yet
- Stocks and calibration profiles (`backend/main.py`, `backend/storage.py`, `backend/validation.py`, `docker/backend/Dockerfile`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `GET`, `POST`, `PUT`, `PATCH` and `DELETE` under `/v1/stocks` and `/v1/calibrations` store StockSpec documents and CalibrationSpec profiles in the same SQLite database as the template catalog, one table each through a shared `Database` and `DocumentStore`, so the two resources answer the same `201`, `404`, `409`, `422` and `204` the templates resource does; each takes its id from `document.metadata.id` (§9.3), validates bodies against its published domain schema with a `422` detail that names the document that failed, answers `409 Conflict` for a create whose identity is stored and for a replace whose document names another identity, `404` for an unknown path id, and `PATCH` merges the fields OpenAPI's `StockPatch` and `CalibrationPatch` publish — `name`, `description` and `tags` in StockSpec `metadata`, and `name`, `description` and the root `enabled` flag for a CalibrationSpec profile; the collections take the §6.1 `page` / `page_size` / `sort` parameters plus the stocks `filter` and the calibrations `printer_id`, and `AR-104` becomes the ninth `CP-API` conformance case; the image copies the two schemas the new operations validate against
- Pagination links (`backend/main.py`, `specs/api/openapi.yaml`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `GET /v1/templates` now carries the API §6.3 `Link` header — `rel="next"` while a next page exists and `rel="first"` when the request is not on the first page, each target keeping the caller's `page_size` and any `sort` / `filter` so following it stays in the same collection, and no `Link` at all when the collection fits on one page because the relations name other pages; the OpenAPI response documents the header with the section's example, and `AP-111` becomes the eighth `CP-API` conformance case — page 2 of 3 must carry both relations, and each target must answer the page it names at the same page size
- Pagination arithmetic case (`tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `AP-110` is now runnable because the templates resource stores documents, so the case seeds 127 templates and asserts the collection's arithmetic where it can be wrong — `page=3&page_size=50` answers 27 items on page 3 of 3 with `has_next: false` and `has_previous: true`, the defaults are 20 items over 7 pages with the first page reporting no previous page, the last page holds the remaining 7, every page reports its own neighbours, walking all seven pages yields each id exactly once, and a `page` of 0 or a `page_size` of 101 answers `400`; the published verification had been unreachable while the catalog could only be empty
- Stateless validation case (`tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `AQ-101` is now a conformance case, because a stored catalog makes the operation's own guarantee observable — a valid document whose `id` equals the path answers `200` with the published `ValidationSuccess` body and creates no template (`GET /v1/templates/{id}` still answers `404`), a document naming another id answers `409` as an `application/problem+json` conflict, and with a template stored at the path id an invalid body still fails with `422` and a valid body leaves the stored document unchanged, so the operation neither reads nor writes the catalog; the case is registered with the RFC-0001 requirement it verifies and `CP-API` stays unclaimed
- Stored templates (`backend/main.py`, `backend/storage.py`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): the templates resource now stores RenderSpec documents instead of listing an empty catalog — `POST /v1/templates` validates the body against the published schema before storing it and answers `201` with the `Template` resource, `422` for a document that fails the schema, and `409 Conflict` for an id already in the catalog (`AR-103`, `AR-106`); `GET /v1/templates/{id}` answers `200` or `404`, `PUT /v1/templates/{id}` revalidates and replaces the document, answering `409` when `document.id` names another identity before it answers `404` for an unknown path id (`AR-102`), `PATCH /v1/templates/{id}` merges the `name` and `description` that OpenAPI's `TemplatePatch` publishes — both RenderSpec root properties — and validates the merged document before storing it, and `DELETE` answers `204` or `404`; the collection reads the store and now honours the `sort` and `filter` parameters it previously accepted and ignored, newest first by default with the id breaking ties, an unknown sort field answering the Section 5.2 `400`. The catalog is a SQLite database (`backend/storage.py`) named by `OPENLABEL_DATABASE` and process-local when that is unset, keeping only the identity, the document and the Section 7.1 timestamps, with `object` derived; `AR-101`, `AR-102`, `AR-103` and `AR-106` become conformance cases and `CP-API` stays unclaimed
- Templates collection (`backend/main.py`, `tests/test_api_app.py`, `tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `GET /v1/templates` now answers the API §6.2 paginated list envelope — `object: "list"`, `data`, and a `pagination` object whose `page` and `page_size` default to `1` and `20`, whose `total_pages` is `ceil(total_items / page_size)` and whose `has_next` / `has_previous` follow from them — and answers the §5.2 `400` bad-request problem document for a `page` or `page_size` outside the §6.1 bounds, rather than FastAPI's own `422` body; there is no store and no operation creates a template, so the catalog it lists is empty and the handler says so, which leaves the persistence layer to replace the source of `data` and `total_items` without changing the contract; `AP-101` now runs the requirement's published verification verbatim — `GET /v1/templates` succeeds under the prefix and an unversioned `GET /templates` does not — instead of observing the prefix on the validate operation, so the recorded narrowing is gone, and `CP-API` stays unclaimed
- Error type coverage (`tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `AP-105` now passes for every status the service can emit — a body that is not JSON answers `400` with the `bad-request` type, an unknown path `404` with `not-found`, a document id that differs from the path id `409` with `conflict`, and a schema-invalid document `422` with `validation-error`, each compared against the URI API §5.2 publishes rather than against `backend/problems.py`, so a table that drifted from the specification fails; `401`, `403`, `429`, `500` and `503` need the authentication, rate-limiting or rendering layers `GET /v1/info` still reports as absent, so the case asserts the four reachable statuses without claiming the rest and `CP-API` stays unclaimed
- Validation error details (`tests/conformance/api_cases.py`, `tests/conformance/cases.json`): `AP-106` now passes — a schema-invalid RenderSpec posted to `POST /v1/templates/{template_id}/validate` must answer `422` with a non-empty `errors` array whose entries each carry a string `field` and a string `message`, so the API §5.3 field-level detail the operation produces is asserted by the conformance suite rather than only by the pytest suite; the check reports every entry it observed, and `CHECKLIST.md` records the requirement as covered
- Stateless template validation (`backend/main.py`, `backend/validation.py`, `docker/backend/Dockerfile`, `tests/conformance/api_cases.py`): `POST /v1/templates/{template_id}/validate` now validates a submitted RenderSpec against the published `specs/renderspec/schema.json` through `jsonschema` — the rules are the schema file itself, not a second definition in code — and answers `200` with `{"valid": true}`, `422` with the API §5.3 body (`Validation Error`, one `errors` entry per failing field carrying a dotted path, the failing keyword and the message) for a schema failure, `409 Conflict` when `document.id` differs from the path id (RFC-0001), and `400` bad-request for a body that is not JSON (§5.2); the operation loads and stores no template, so it never answers `404`; `problems.problem_response` gained the `title` and `errors` parameters §5.3 needs, the `app` image copies the schema next to `backend/` and `backend/requirements.txt` pins `jsonschema`, and `AP-104` becomes the third `CP-API` conformance case — a `404` and a `422` both asserted to be `application/problem+json` with `type`, `title` and a `status` equal to the HTTP status, which is the first time the suite can observe the `422` half
- Entrypoint smoke test (`tests/test_api_app.py`, `docker/ci/requirements.txt`): the suite now starts the service the way the container does — `uvicorn backend.main:app` on a free loopback port, waiting for `/v1/info` to answer and stopping it afterwards — so the module path, the ASGI server and the version header are exercised as a process, not only through an in-process test client; CI installs `uvicorn` for it
- Health endpoint (`backend/main.py`, `docker/backend/Dockerfile`, `tests/conformance/api_cases.py`): `GET /v1/health` answers `200` with `{"status": "ok"}` under the `/v1` prefix, needs no credentials and checks no dependency, and the `app` stage of the backend image now overrides the inherited `HEALTHCHECK` to probe `/v1/health` — the stub stage keeps `/health`, which its placeholder server answers and which the application deliberately does not serve (API §3.1) — so a container built with `BUILD_TARGET=app` no longer reports unhealthy against a path nothing answers; `AP-103` is the second `CP-API` conformance case and the pytest suite validates the body against the OpenAPI `HealthResponse` component and pins `/health` as an unversioned path that must not answer
- Backend service skeleton (`backend/main.py`, `backend/problems.py`, `backend/requirements.txt`): a FastAPI application serves `GET /v1/info` under the mandatory `/v1` prefix with `api_version`, `server_version`, the domain specification versions and honest capabilities (no rendering, printing or authentication yet), stamps `X-API-Version: 1.0` on every response through middleware and on the handlers the middleware never sees, and answers every error — unknown path, unsupported method, unexpected failure — as an RFC 9457 `application/problem+json` problem document whose `type` comes from the API §5.2 table (`about:blank` for a status it does not name) with `status` repeating the HTTP status; no unversioned route answers, FastAPI's own `/docs` and `/openapi.json` routes are off because the published contract lives in `specs/api/`, and `tests/test_api_app.py` validates the bodies against the OpenAPI components while the conformance suite gains its first `CP-API` case, `AP-102` (`tests/conformance/api_cases.py`)
- Miskeyed subset cache mutation (`tests/conformance/mutations.py`): the harness now also keeps one font subset for the whole case and requires the `DT-105` case to catch it — that case renders one glyph set under two clocks and then a smaller set, so a cache that never rekeys hands the smaller document the earlier subset, the two keep one tag, and the case fails naming it; the breakage replaces `renderer.fonts.Sfnt.subset`, is restored afterwards like the others, and takes the harness to five breakages whose owning cases must all report them
- Active boundary coverage (`RO-112`, `tests/conformance/renderer_cases.py`): the suite now paints a full-bleed fixture — a black rect that overruns a 40 x 30 mm label by 5 mm on every side and carries a 4 mm stroke — renders it to PDF and PostScript and rasterizes both at 1200 dpi, then requires the label to be black half a millimetre inside each edge and the page margin 2.5 mm outside it to stay blank; a body clipped to the page instead of the label, a clip that is inset, or a stroke that escapes the clip all fail, so `RO-112` moves from open to covered
- Colour space coverage (`RO-105`, `tests/conformance/renderer_cases.py`): the suite now paints five fixed swatches — pure red, green, blue and black, and mid grey — and reads every colour operator back out of both artifacts: the PDF must set them with `rg`, `k` and `g` for `output.color_space` `rgb`, `cmyk` and `grayscale`, the PostScript with `setrgbcolor`, `setcmykcolor` and `setgray`, neither artifact may carry an operator from another space, and every channel must equal the documented conversion (sRGB unchanged, the BT.601 luma `0.299 R + 0.587 G + 0.114 B`, and `K = 1 - max(R, G, B)` with `C = (1 - R - K) / (1 - K)`) — so a writer that ignores `color_space`, leaves sRGB values under a `k` operator or drops a luma coefficient fails instead of producing a plausible page; the implementation already converted every paint this way, so the change is coverage only and ConformanceSpec `RO-105` moves from open to covered
- Environment independence coverage (`DT-106`, `tests/conformance/renderer_cases.py`): the suite now renders one document in four separate interpreters and requires the same digests from each — the current environment, a `+05:45` timezone with a comma-decimal locale and hash seed 1, a `-03:30` timezone with a Turkish locale and hash seed 2, and UTC with the C locale and hash seed 0 — with the last one run from a working directory that holds a space and the middle two from outside the repository, so a locale-dependent number format, a local-time identifier, a set whose order follows `PYTHONHASHSEED`, or a relative path resolved against the working directory fails the suite; the implementation already ignored all of them, so the change is coverage only and ConformanceSpec `DT-106` moves from open to covered
- Font subset determinism coverage (`DT-103`, `tests/conformance/renderer_cases.py`): the suite now sets `AB` then `ü` in the registered `Probe Sans` face in one document and `ü` then `AB` in a second, requires the two artifacts to differ so the paint order really moved, and extracts each PDF's `/FontFile2` program: the two must be byte-identical, carry the same four glyphs (`.notdef`, `A`, `B`, `ü`) and stay smaller than the source face — so a subsetter that orders glyphs by first use, keys a cache on the run rather than the glyph set, or lets the object order reach a table fails instead of producing two valid-looking subsets; the implementation already sorted the characters and glyph ids it keeps, so the change is coverage only and ConformanceSpec `DT-103` moves from open to covered
- Content-derived identifier coverage (`DT-105`, `tests/conformance/renderer_cases.py`): the suite now renders the registered `Probe Sans` face twice, once with the clock pinned to a 2023 instant and `os.urandom` returning zero bytes and once with the clock pinned to 2039 and the random source returning `0xFF`, and requires identical bytes and the same six-letter subset tag both times — so a writer that stamps an identifier from a clock or a random source fails. It then renders a smaller character set and requires a different tag, so an identifier that is merely constant is not mistaken for a content-derived one. The subset tag already came from the program's digest, so the change is coverage only and ConformanceSpec `DT-105` moves from open to covered
- Conformance mutation checks (`tests/conformance/mutations.py`, `tests/test_conformance_mutations.py`): the suite now proves that its renderer cases can fail — each of four named breakages replaces one renderer attribute and the case that owns the property must pass unbroken, then fail while it is applied, with a detail that names the breakage, before the original is restored. The breakages are a group's matrix, opacity and visibility ignored and a creation timestamp written into the PDF, caught by `RT-117`, `RT-108`, `RT-107` and `RO-110` respectively; `scripts/test.sh` runs the harness and its unit tests, so a case that quietly stops being able to fail fails the build, and the harness is documented in the conformance README
- Compression determinism coverage (`DT-104`, `tests/conformance/renderer_cases.py`): the suite now renders one document twice with `compress: true` and reads every `/Filter /FlateDecode` stream back out — the two artifacts and their streams must be byte-identical, every stream must inflate, and neither the artifact nor its decompressed operators may carry `/CreationDate`, `/ModDate` or `%%CreationDate`, either of the document's own `created_at` / `updated_at` values, the repository path or the working directory; the zlib header may not declare a preset dictionary, so a stream that embeds a local-time stamp, a path or a dictionary the reader must supply fails instead of passing a byte comparison against another equally tainted render. The writer already deflated at a fixed level with no header of its own, so the change is coverage only and ConformanceSpec `DT-104` moves from open to covered
- Concurrent render coverage (`DT-107`, `tests/conformance/renderer_cases.py`): the suite now renders one document ten times at once, five to PDF and five to PostScript, all released on one barrier, and requires every digest to equal the serial render's and a later serial render to be unchanged — so a shared mutable cache, a reused writer buffer or a subsetter that keeps state between calls fails the suite instead of passing `DT-101`'s two sequential renders; the implementation already kept no render state between calls, so the change is coverage only and ConformanceSpec `DT-107` moves from open to covered
- Group inheritance coverage (`RT-117`, `tests/conformance/renderer_cases.py`): the suite now checks that a `group`'s transform, visibility and opacity reach its descendants instead of each object being composed on its own — a 0.5-opacity group at `(5, 5)` rotated 90° carries its child's anchor to `(-5, 15)` and its local `(10, 0)` corner to `(-5, 25)` at alpha 0.5, a group nested inside it adds its own translate and rotation to land a grandchild at `(5, 15)` at alpha 0.25, and a hidden inner group draws nothing; the implementation already behaved this way, so the change is coverage only and ConformanceSpec `RT-117` moves from open to covered
- Barcode decode verification (`RO-107`, `tests/conformance/barcode_reader.py`, `tests/conformance/renderer_cases.py`): the suite now reads rendered barcodes back from their pixels instead of only checking the patterns it planned — each of the eight linear symbologies and the stacked `pdf417` renders to both artifacts, rasterizes at 600 dpi, and decodes with readers that fit the scan line to one module grid, invert the standard's published pattern tables (ISO/IEC 15417, 16388, 15420, 16390, 16389 and 15438) and compute their own modulo-10 and modulo-103 check digits, so an EAN/UPC check digit, every character and the painted box within 0.1 mm must all come back; `pdf417` also yields its row indicators, its byte-mode text and a zero Reed-Solomon syndrome at every generator root, so `RO-107` moves from open to covered
- QR decode verification (`RO-108`, `tests/conformance/qr_reader.py`, `tests/conformance/renderer_cases.py`): the conformance suite now reads a rendered QR symbol back instead of only checking the grid it encoded — at each error-correction level it renders a 25 mm symbol to both artifacts, rasterizes it at 600 dpi and decodes it from its pixels with an ISO/IEC 18004 reader that locates the finder and timing patterns, measures the module grid, reads both format-information copies (level and mask), unmasks the data area, walks the two-module zigzag and parses the byte-mode segment. The reader shares no table with `renderer/qrcode.py` and covers the single-block versions 1 and 2. It also evaluates the whole codeword block at every generator root in GF(256), so the Reed-Solomon syndromes must be zero: it reports the degree it checked, and rejects a symbol whose first error-codeword module is flipped in the raster even though its data codewords still decode. The content, the level the format information names, the 25 x 25 module grid and the painted extent within 0.1 mm must all come back, so `RO-108` moves from open to covered
